# 大型可组合 AI 插件的设计与维护

[English](COMPOSABLE-PLUGIN-DESIGN.md) | **简体中文**

修改本设计时，请同步维护中英文版本。

状态：推荐工程方法，2026-09-14。这是一份可复用的设计参考，不代表已经安装的框架、新协议或生产验收结论。[Bug Bash 架构](BUG-BASH-ARCHITECTURE.zh-CN.md)将此方法应用于无障碍问题发现。在经过单独评审的实现变更生效前，现有产品与部署契约仍然有效。

## 1. 方法：受约束的自适应

让模型推理发现有价值的工作、提出能力组合；让可信运行时强制执行授权、契约、资源归属、外部作用核对和完成条件；让经验改进未来的候选方案，而不是悄悄改写当前运行的规则或实现。

目标是在明确预算内得到有用、有证据支持的结果，而不是增加插件、Agent、工具调用或发现数量。这是面向有状态、会作用于外部系统的助手的工程综合方案，不是经过证明的普适最优解，也不是替换现有可用 Harness 的理由。

围绕可验证的工作单元设计：

> 前置条件 -> 操作 -> 预期结果 -> 所需能力 -> 证据 -> 复位/清理。

把用户要的结果与当前实现分开。更换模型或 provider（能力提供方）后，仍应依据同一份已接受的工作与证据要求评价。选择编排框架之前，先定义支持范围、不支持的情况、授权、预算和终态。

## 2. 分清三种边界

| 边界 | 何时拆分 | 不要假定 |
|---|---|---|
| 分发/插件 | 独立复用、发布周期、权限或宿主集成需要稳定的包 | 每项能力都需要一个安装包或 MCP 进程 |
| 推理上下文 | 较大的程序性任务有完整输入、有界结果，且很少需要共享中间推理 | 每个插件都需要 Agent；层级越深越好 |
| 执行/授权 | 真实外部作用、凭据、资源归属或隔离要求受控 provider | 新的模型上下文可以隔离共享浏览器、桌面、数据库或账户 |

跨步骤的规范与路由知识保留在主上下文中。适合自包含分析、且能从干净上下文中获益的任务，才采用隔离推理。查询、哈希、校验等非推理操作使用确定性工具。如果子代理不可用，在宿主允许时保留正确的主上下文执行路径；绝不虚构独立评审者。

隔离的子任务需要适用性说明、完整任务输入、过程、输出 schema、终止条件和有界证据指针。默认返回结果及可展开的来源，而不是完整子任务对话。明确声明不确定性，不要让父任务猜测缺失上下文。

只有出现稳定的独立消费者或运维边界时，再决定抽取安装包。先使用共享源模块，不要把同一实现复制进编排包和多个兄弟包。

## 3. 通过稳定服务契约组合能力

分离服务定义、提供方和消费者。消费者通过稳定服务标识取得能力，声明式依赖决定何时激活。保持执行循环可替换，不把领域逻辑耦合到特定框架。

| 机制 | 可复用的设计规则 |
|---|---|
| 稳定服务标识 | 消费者请求版本化能力契约，而不是具体实现名称 |
| 声明式依赖 | 所需服务可用后才激活；缺少可选能力只影响依赖它的工作 |
| Profile 与 bundle | Profile 指定支持的组合；bundle 分发实现与配置。两者都不能证明现场可用 |
| 可撤销注册 | 每个插件都有明确归属的生命周期，以及参与注册项/资源的释放路径 |
| 可替换循环与模型 profile | 任务/领域逻辑不写进模型循环；在可行时把模型差异数据化 |
| 上下文与缓存契约 | 除功能行为外，还说明模型可见内容、渐进披露阶段、token 成本和缓存影响 |

服务名称不构成对某个实现的授权。由操作者控制的绑定和运行时允许列表决定哪些 provider 可以执行。在产生外部作用前，拒绝提供方歧义、版本不兼容、硬依赖缺失或循环依赖。

确定性地解析 profile/配置层，并记录最终绑定及其来源。模型可以建议允许的能力，但不能通过提示修改可执行路径、权限或 provider 配置。优先使用当前宿主支持的 manifest/注册表；概念上的服务契约不会自动成为 Copilot manifest 的新字段。

每次接受的运行都要固定实现、契约、skill、模型/配置、profile 和检索版本。如果无法获得精确的后端模型身份，记录公开的身份及不确定性，不要虚构可复现快照。使用前刷新实际执行宿主的就绪状态。更新通常只服务于新运行；迁移正在进行的运行，需要显式核对外部作用，并保持状态与证据语义兼容。

释放注册项不等于取消或回滚任意外部作用。移除监听器不能撤回已经发出的消息；注销 provider 不能停止远端作业或释放租约。插件替换不能使未完成任务唯一的监督器失效。插件机制不是安全沙箱，也不是系统可靠性的证据。

## 4. 让能力契约可用于实际运行

为每项可独立调用的能力记录以下信息，再引入兼容的 schema 实现：

| 契约领域 | 必须回答的问题 |
|---|---|
| 身份 | 稳定的服务/操作 ID、schema 版本、provider 实现/版本/摘要 |
| 适用性与输入输出 | 何时应该调用？接收/返回哪些完整输入、结果、错误和来源信息？ |
| 推理 | 主上下文知识、隔离过程还是确定性工具？哪些内容必须留在父上下文？ |
| 外部作用与授权 | 只读还是修改？所需权限、资源亲和性/互斥及强制执行位置是什么？ |
| 生命周期 | 支持哪些准备、执行、核对、取消、清理操作？幂等边界、期限和结果未知时的行为是什么？ |
| 证据 | 什么证明操作确实执行过？另有什么证明它声称的结果？ |
| 上下文与成本 | 何时披露元数据/说明/产物？上下文和总 token 预算、延迟及缓存敏感性如何？ |
| 验收 | 哪些宿主/profile/版本组合有真实证据，哪些不支持？ |

估算与实测成本要分开。父上下文峰值、累计输入/输出 token、缓存复用和墙钟时间是不同指标；子代理可能降低前者，却增加后几项。不要把秘密写入 manifest、提示、成本记录或回执。

## 5. 在线组合：先提议，再确定性接受

```text
已授权任务 + 适用知识
          |
          v
可验证工作计划 -> 有界能力检索
          |             |
          +-------------+
                 v
契约 / 授权 / 资源 / 预算校验
                 v
已接受、绑定版本的计划 -> 受控执行
                 v
证据完整性 + 独立结果评估
                 v
完整核算的结果 + 清理 + 交付
```

维护两类不同关系。它们可以共享存储，但绝不能共享授权效力：

- **硬约束：** 显式服务前提、权限、资源独占、必做工作、证据要求和已批准预算。
- **软经验关系：** 相关性、有用的顺序、可能的共同使用、观测成本和检索描述。它们只建议候选与优先级。

学习到的共现关系不是经过认证的依赖、不兼容关系或权限。必须能区分声明的关系与推断的关系。学习得到的排序不能因为某项必做工作少见、昂贵或困难就删掉它。检索失败时，只有满足同一范围与契约的已验收静态组合才可作为回退，否则必须明确报告缺少的能力。

先用小型显式能力目录和静态 profile。只有能力库规模或实测选取失败证明有需要，才增加图检索。有界 top-k 候选列表不是遗漏必需能力的理由。

规划过程中可能发现更多工作。应追加获得授权的计划修订，保留稳定工作 ID、理由、前提、证据要求和剩余预算；不能覆盖历史行或已接受回执。每个已提交操作保持原始绑定。不能静默扩展任务预算，必须为核对、清理与交付预留容量。

调度依据是真实资源独立性，而不是可用 Agent 数。只有工具和外部作用互不干扰时，并行分析才有意义。

## 6. 可靠执行不能依赖对话记忆

复用真实的归属与操作存储，不要引入竞争性的租约权威。在模型上下文之外保存持久化的 task/run/step/request 身份、只追加的状态迁移历史和可重建的当前状态。提交前保存精确的外部作用意图。

超时后，保留请求身份并核对原操作。只有 provider 契约已经证明重试安全，才可以重试。持久日志本身不能保证外部作用恰好发生一次。重放已接受的计划和观测，不要让新模型重建之前的推理。

准入无人值守执行时，必须具备正常工作的执行器、持久进度、完成通知和独立停滞检测。提示、心跳或运行中的 PID 都不能证明进展。保存精确下一步、恢复条件和期限。采用有界、改变假设的恢复；身份验证/同意和授权边界是真正的停止条件，不是需要绕过的障碍。

取消操作只作用于精确授权的任务及其自有子任务。停止维护不能停止无关 feature 任务。没有获得授权的替代路径时，不能移除未完成任务唯一的续跑路径；反之，也不能借新 watcher 重启已被明确取消的工作。核对外部作用并完成清理后，才能关闭资源归属义务。

分别定义执行、结果覆盖和交付的终态。操作失败不是产品问题；交付部分报告，也不代表完全完成或可以放弃尚未核清的外部作用。

## 7. 分离记忆、证据与权威状态

| 记录 | 用途 | 不能证明 |
|---|---|---|
| 原始轨迹与产物 | 带原始来源/会话/时间出处，展示记录了什么 | 仅凭日志就证明当前真实状态、当前权限或不可篡改的行为 |
| 整理后的程序性知识 | 解释适用过程和过去的恢复经验 | 当前资源健康，或重放归档命令的授权 |
| 权威执行状态 | 确定归属、已接受工作和待核清外部作用 | 没有支持证据时证明观测行为正确 |

采用简短检索结果，并允许展开原始段落。应用可见性控制、来源和新鲜度检查。把检索内容视为不可信证据，而不是可执行的授权依据。不能因为云记忆服务支持私有数据集或凭据扫描，就导出私有轨迹。必须确认工具/Agent 与实际宿主兼容。

确定性地校验产物身份、schema、字节和绑定。另行评估这些产物是否支持结论，使用独立评判标准，以及在需要时使用经过资格确认的评审者。第二个模型重复第一个模型的结论，不构成充分独立性。哈希是完整性校验，不是行为真实性或外部见证的保证。

## 8. 离线改进，而非不受约束的自我修改

分开优化能力检索/关系、skill 过程文本、provider 实现和评价标准。最初每次只改变一个层面，以便归因。优化器不得修改用来评判自身结果的评价标准或硬性政策。

1. 收集已授权的轨迹、失败、成本与来源；区分产品、基础设施和评价失败。
2. 基于观测证据选择有界改进目标，而不是追求新奇。
3. 提出版本化的图/描述或 skill 修改。保留问题历史、被拒尝试、回归和复发。
4. 在同一环境和预算下比较基线与候选。使用独立回归集和留出用例，而不只是促成这次修改的用例。
5. 只有受保护行为保持不变、报告不确定性且声明目标得到改善时才接受，否则保留旧版本。
6. 通过经过评审的变更和已验收 profile 发布，并提供回滚。只对新运行推广；记录决策和停止条件。

结果方差需要时，采用重复配对试验。即使另行报告产品准确性指标，也必须把基础设施失败计入端到端可靠性。跟踪误报、测试样例中的已知漏报、有结论覆盖与已尝试覆盖、重复外部作用、归属违规、恢复/清理/交付、人工介入及成本。不能最大化报告缺陷数，也不能悄悄丢掉困难工作来缩小分母。

限制评估窗口，回归时停止，并保留回滚路径。不允许持续进行未经评审的 skill 图演进。

## 9. 采用与维护顺序

| 阶段 | 交付物 | 满足什么条件才能推进 |
|---|---|---|
| 可靠纵向切片 | 一个静态支持 profile，具备真实产物和如实的失败结果 | 正常/缺陷用例、恢复、清理和交付正常工作 |
| 显式组合 | 可复用服务契约、声明式依赖和版本化工作计划 | 安全拒绝非法输入、缺失/歧义 provider、重复外部作用和归属冲突 |
| 有界自适应 | 在已验收能力中按任务选择并修订计划 | 必做工作保留；相同预算下优于静态 profile |
| 证据驱动演进 | 离线图或 skill 候选变更 | 独立回归/留出集支持收益，且回滚保持受保护行为 |

每次维护变更都记录：受影响能力与消费者；契约/权限/上下文影响；新运行与当前运行的不同行为；验收证据；发布/回滚责任方；尚未解决的限制。演练作用发生过程中重启、回调丢失/重复、取消无关任务、运行时过旧和清理失败。插件数量与 Agent 数量是优化选择，不是发布门槛。

Feature/设计文档正文聚焦需求、决策、接口、执行和验收，不穿插文章摘要、资料比较或阅读过程。必要的来源链接和证据限制放在文末参考资料中；较长的研究讨论放在独立文档。
