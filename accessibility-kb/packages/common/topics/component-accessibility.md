# Component semantics

## Review trigger and evidence scope

Apply this review to every added or changed rendered UI surface affecting
interaction, semantics, assistive output or accessibility-relevant styling:
contrast/forced colors, focus indicators, typography/spacing, zoom/reflow,
overflow/truncation, visibility, content order, targets, motion and state cues.
Include forms, transient surfaces, dynamic status and async collections even
when the diff contains no explicit accessibility code. Decorative-only spacing,
radii or shadows are outside this trigger only with evidence that they cannot
affect clipping, reflow, targets, focus, readability or semantics.

The migrated AgentOW review policy checks applicable WCAG 2.1 A/AA criteria and
complete keyboard-only and screen-reader operation for affected UI. Record
not-applicable only with a diff-based explanation establishing no rendered UI,
interaction or assistive-output impact. Record runtime-dependent criteria as
not verified until appropriate evidence exists; source inspection is not a
conformance pass. A current product may require a newer or additional standard;
use `common.requirements.authority-and-applicability` to resolve that scope.

Basis: [review trigger and evidence policy](https://github.com/kaixun96/dev.AgentOW/blob/7896845e51d75b0b9d632a2fd61876bc2f556ea5/copilot/skills/ow-review/references/accessibility.md#L1-L19).

## Native semantics before custom behavior

Match the element to its purpose: links navigate, buttons perform actions,
checkboxes represent independent selections and radio buttons represent a
single choice in a group. Prefer native controls or a suitable component already
used by the project. A clickable generic container is not made fully accessible
by adding a role alone.

```html
<!-- Action: no custom role or keyboard emulation is needed. -->
<button type="button">Save</button>

<!-- Navigation: keep a real destination. -->
<a href="/settings">Settings</a>
```

Inspect event wiring in the surrounding source before concluding these controls
work. Conversely, do not flag a native button for lacking an explicit Enter
handler or an `aria-label` when its visible text already names it.

## Names, descriptions and relationships

- Every user-operable control needs a meaningful accessible name. Prefer visible
  text and native labels; icon-only controls need an appropriate naming mechanism.
- Keep the visible label in the accessible name where the criterion applies.
  Avoid an `aria-label` that silently replaces useful visible wording.
- Descriptions provide additional instructions, not a duplicate of the name.
  A placeholder or tooltip is not a reliable replacement for a field label.
- Trace `aria-labelledby`, `aria-describedby`, label `for` and related IDs.
  A provably missing target or duplicate ID is a source-supported issue; IDs
  generated by an unknown wrapper are context needed, not automatically broken.
- Preserve required parent/child relationships and semantic grouping.
  Do not use presentational roles or hidden wrappers to mask a semantic problem.

```html
<button type="button" aria-label="Close">
  <svg aria-hidden="true" focusable="false" viewBox="0 0 16 16">
    <path d="M4 4 L12 12 M12 4 L4 12" />
  </svg>
</button>
```

The wording is illustrative; follow the project's localization conventions.

## State must match behavior

Follow state values through all reachable branches: expanded/collapsed,
selected, checked, pressed, invalid, required, busy and disabled. Use only the
attributes valid for the element's role and the platform's supported semantics.

`aria-disabled="true"` communicates a state but does not disable event handlers.
When it is used instead of native `disabled`, inspect whether activation is
actually prevented. Do not assume every disabled control must remain focusable;
follow the intended control pattern.

`aria-hidden="true"` does not remove a focusable descendant from keyboard order.
Flag a source path that leaves an interactive element focusable in a hidden
subtree. Distinguish this from content intentionally removed from rendering or
made inert; final accessibility-tree behavior is not proven by static inspection.

## Structure and reusable components

- Use headings for section structure rather than choosing levels for font size.
  Derive a level from the available parent/sibling context. If only an isolated
  component is provided, record that the page outline is unknown; do not invent
  a heading level or enforce a universal single-heading rule.
- Preserve list and table semantics where the data has those relationships.
  An interactive grid needs a full interaction contract, not just `role="grid"`.
- Use landmarks and distinguish repeated regions when it helps orientation;
  avoid adding a named region to every decorative wrapper.
- Check whether props reach the semantic element through slots, wrappers,
  forwarding and composition. Do not assume an unfamiliar component renders
  a particular tag or forwards arbitrary ARIA props.
- Reuse documented native/library naming, focus and state behavior. Adding a
  second role, live region or focus owner can break an already valid component.

When a component's implementation or documented contract is unavailable, report
context needed. No repository-specific library is a prerequisite for this topic.

## Concrete rendered-contract checks

The following are **draft, generalized historical guidance**, not newly approved
standards mappings. Inspect the rendered semantic element and its descendants,
not only JSX props. These examples specify expected verification, not results.

| Contract | Positive verification example | Negative example / risk to distinguish |
|---|---|---|
| Action versus navigation | Save exposes a button; Settings exposes a link with a destination; each has its expected keyboard behavior | A clickable span has a button role but no Space activation, or a navigation action loses link behavior |
| Name and additional context | An icon-only Close action has a localized name; a visible Rename label remains in its name; a description adds a necessary consequence | An unnamed icon, an unrelated overriding label, or the same text repeated through label and description |
| Named group | Related delivery choices expose a group named Delivery method through a legend or the component's supported relationship | A nearby visual heading is mistaken for a programmatic group name; `aria-describedby` is used alone where a name is required |
| State and value | After opening Filters, the trigger exposes expanded state and its supported panel relationship; radio/checkbox/pressed/selected values match the committed choice | Visible selection changes but the semantic state is stale; a wrapper overrides the child's correct role or state |
| Structural relationships | A data table exposes column/row headers for its cells; tabs identify their panels; a dialog has a contextual label | A layout-only grid gains interactive-grid semantics without its keyboard model, or headers/relationships are lost in wrappers |
| Presentation and hiding | A genuinely decorative wrapper loses no required relationship; a decorative icon inside a named button does not add speech | `role="none"` or `role="presentation"` is applied to a focusable control or required table/list structure; an apparently hidden subtree still contains reachable controls |
| Heading and region context | A section/dialog title uses a semantic heading at a level justified by its parent and siblings; region names distinguish useful areas | Font size chooses the heading level; a wrapper erases section semantics; every layout box becomes a landmark |
| Transient surface | A named trigger and surface preserve the documented opening, dismissal, state, and focus contract | A styled dialog/flyout shell is assumed accessible despite a missing title relationship or broken trigger composition |

Check expanded, selected, checked, pressed, invalid, required, busy and disabled
states only where supported by the actual role. Lack of explicit caller ARIA is
not a failure if native/component output already supplies the contract. A
presentational role is not automatically wrong on a truly presentational element;
confirm what the platform exposes instead of assuming either suppression or safety.

For a custom control justified by a documented native/library gap, specify all of
name, role, value, relationships, keyboard reach/operation/dismissal, focus,
disabled activation, pointer operation, state feedback, forced colors and tests.
A working click handler plus one ARIA attribute is not that contract. Keep simple
tabular data a table unless the experience actually requires a composite grid.
See [caller responsibilities](../implementation/component-contract.md),
[form/content cases](forms-and-content.md) and [focus lifecycle](keyboard-focus.md)
for their detailed checks rather than duplicating implementations here.

## Heading-level changes need the surrounding outline

Before recommending or implementing a heading-level change, capture the complete
live page/dialog outline, target heading, nearest parent, relevant siblings,
selected level and rationale. Missing or ambiguous context makes that proposed
change inconclusive: do not choose a level until the context is resolved.
After the change, recapture the same scenario and compare that outline, not only
the edited element. A component-only snapshot cannot establish page hierarchy.
For example, a proposed H3 is justified by the actual H2 section parent, not by
its font size; without that parent/sibling evidence, defer the level decision.
This preserves the source's evidence decision without prescribing a repository
artifact filename or a universal single-H1 rule.
